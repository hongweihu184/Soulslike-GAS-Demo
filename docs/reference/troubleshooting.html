日常编译工作流(背下来,80% 的问题不会发生)

编译只认两条路

场景操作
UE 编辑器开着保存代码(Ctrl+S)→ 编辑器里按 Ctrl+Alt+F11(Live Coding 热补丁)
编辑器关着命令行 UBT 全量编译(命令见 P3);或 VS 里右键 ProjectUnreal 项目 → 生成

三条铁律

  1. 永不点"生成解决方案"——只生成 ProjectUnreal 项目。引擎自带的测试项目在启动器版引擎上永远编不过,与你的代码无关。
  2. 判断代码对错只看编译结果(UBT 输出 / Live Coding 弹窗),VS 红波浪线是 IntelliSense 的猜测,仅供参考。错误列表筛选设"仅生成"。
  3. 新建 C++ 类 / 加插件 / 红线异常增多 → 重新生成工程文件: 
    /e/UE_5.8/Engine/Binaries/ThirdParty/DotNet/10.0/win-x64/dotnet.exe \
  /e/UE_5.8/Engine/Binaries/DotNET/UnrealBuildTool/UnrealBuildTool.dll \
  -projectfiles -project="E:\UE5.8Project\ProjectUnreal\ProjectUnreal.uproject" -game -rocket -progress
血的教训:不要碰引擎目录里的东西。E:\UE_5.8\Engine\ 下的缓存/标记文件(Intermediate/Build/BuildRules、InstalledBuild.txt)删了会导致引擎自身无法构建,修复只能靠 Epic 启动器"验证"。要清理只清工程目录(E:\UE5.8Project\ProjectUnreal)下的 Intermediate、Binaries、.vs。

P1 · VS 满屏红波浪线 / "无法打开 CoreMinimal.h" 已解决

症状:无法打开 源 文件 "CoreMinimal.h" / "AttributeSet.h";未定义标识符 "GENERATED_BODY";缺少显式类型(假定"int");应输入";"

定性

全部是 IntelliSense 假错误,不是编译错误。VS 的实时分析读不懂 UE 的宏体系。真正的判官是编译器。

快速解法(按顺序试)

  1. 确认文件是从"解决方案资源管理器"里打开的(不是从磁盘拖进来的"杂项文件")。
  2. 重新生成工程文件(命令见"工作流"铁律 3)——最常见有效,刷新 IntelliSense 的 include 路径。新建类/改插件后必做。
  3. 错误列表筛选改"仅生成",只看真编译错误。
  4. 还难受:工具 → 选项 → 文本编辑器 → C/C++ → 高级 → IntelliSense → "禁用错误报告"=True、"禁用波形曲线"=True。
  5. 终极:关 VS,删工程根目录的 .vs 隐藏缓存文件夹,重开等它重建索引。
根治方案:JetBrains Rider for Unreal(非商业用途免费)能真正解析 UE 宏,红线/跳转/补全全部正常。代价:约 10GB 磁盘 + 运行时 4-6GB 内存,16GB 内存机器与 UE 编辑器同开会紧张。

P2 · VS"生成解决方案"一堆项目失败(退出代码 6) 已定性

症状:LiveLinkHub / IoStoreOnDemandTests / EventLoopUnitTests / ChaosTestHarness / DotNetPerforceLib 失败;"Program targets are not currently supported from this engine distribution"

定性

正常现象,永远无视。这些是引擎源码附带的测试/工具程序,启动器版(预编译)引擎本来就不支持编译它们。

正确操作

右键解决方案资源管理器里的 ProjectUnreal 项目(Games 文件夹下)→ 生成。只关心 ProjectUnreal 相关输出行。

P3 · "Unable to build while Live Coding is active" / 退出代码 8 已解决

症状:VS 或命令行编译失败:Unable to build while Live Coding is active. Exit the editor and game

原因

UE 编辑器开着,持有构建锁。外部(VS/命令行)全量编译被拒绝。

解法

二选一:① 在编辑器里按 Ctrl+Alt+F11 热编译(推荐,不用关编辑器);② 完全关闭编辑器再外部编译。

命令行全量编译命令(备查)

/e/UE_5.8/Engine/Binaries/ThirdParty/DotNet/10.0/win-x64/dotnet.exe \
  /e/UE_5.8/Engine/Binaries/DotNET/UnrealBuildTool/UnrealBuildTool.dll \
  ProjectUnrealEditor Win64 Development \
  -project="E:\UE5.8Project\ProjectUnreal\ProjectUnreal.uproject" -waitmutex

P4 · Live Coding 假成功("up to date" 但新代码没编进去) 已解决

症状:Ctrl+Alt+F11 显示 "Target is up to date" "Result: Succeeded",但代码明明是刚改的;伴随 "Unable to parse LiveCoding.json (missing LinkerPath field)"

原因

Live Coding 清单文件(Engine/Intermediate/LiveCoding.json)损坏(通常是被打断的编译造成的),整个热补丁管道空转。"Succeeded"是假象——什么都没编。

验证方法

对比 dll 和源码的时间戳:Binaries/Win64/UnrealEditor-ProjectUnreal.dll 比 Source/ 里的 .cpp 旧 = 新代码没编进去。

解法

  1. 完全关闭 UE 编辑器
  2. 删除 E:\UE_5.8\Engine\Intermediate\LiveCoding.json 和 LiveCodingModules.json(会自动重建)
  3. 命令行全量编译(命令见 P3)
  4. 重开编辑器,Live Coding 恢复正常
防再犯:不要在 Live Coding 补丁进行中强制关编辑器;机器内存不足时(可用 <2GB)尽量避免热编译大改动。

P5 · "Expecting to find a type ... module rules named '插件名'" 已解决

症状:启用某插件后编译失败:Expecting to find a type to be declared in a module rules named 'VisualStudioTools' in 'UE5Rules'

原因

启动器版引擎用预编译好的规则程序集(UE5Rules.dll),它出厂时不包含你后加插件的构建规则。启用插件后 UBT 从旧缓存里找不到规则类。

解法(按推荐顺序)

  1. 如果插件非必需:在 .uproject 里禁用它(删掉对应 Plugins 条目),最快。例:VisualStudioTools 只是 VS 辅助工具,VS2022 17.9+ 已自带虚幻集成。
  2. 如果需要:把插件从引擎目录移到工程的 Plugins/ 目录,让项目规则程序集接管它。
千万别做:不要试图删 Engine/Intermediate/Build/BuildRules 强制重编(会触发 P6),也不要删 Engine/Build/InstalledBuild.txt(会触发 P7 全引擎重编译)。这两个都是 2026-10-05 实际踩过的连环坑。

P6 · "Precompiled rules assembly 'UE5Rules.dll' does not exist" 已解决

症状:编译失败:Precompiled rules assembly 'E:\UE_5.8\Engine\Intermediate\Build\BuildRules\UE5Rules.dll' does not exist

原因

引擎的预编译规则程序集被删了(通常是人为清理 Intermediate 时误删)。启动器版引擎被设计为"不重编此文件",自己补不回来。

解法

Epic Games 启动器 → 库 → UE 5.8 → 下拉箭头 → "验证"(Verify)。扫描几分钟后自动重新下载缺失文件(只有几 MB)。

P7 · 误触发全引擎重编译(几千个任务) 已解决

症状:编译任务数变成几千个([xx/4921]),开始编译 Module.Core.*.cpp 等引擎模块

原因

Engine/Build/InstalledBuild.txt 标记丢失/被改名 → UBT 把引擎当成源码版,尝试重编整个引擎。16GB 内存机器上要跑好几个小时。

解法

  1. 立刻停止编译
  2. 恢复 E:\UE_5.8\Engine\Build\InstalledBuild.txt(内容就一行 UE_5.8;或从 .bak 改回来)
  3. 若规则程序集也受损 → Epic 验证(P6)

P8 · "modifies the values of properties ... not allowed" 已解决

症状:ProjectUnrealEditor modifies the values of properties ... This is not allowed, as ... build products in common with UnrealEditor

原因

Target.cs 用了旧教程的 BuildSettingsVersion.V5,与 UE5.8 引擎共享构建环境冲突。

解法

两个 Target.cs 改为 DefaultBuildSettings = BuildSettingsVersion.V7;。教训:抄旧教程的 Target.cs 模板时,以引擎报错的提示版本为准。

P11 · error C2027: 使用了未定义类型 已解决

症状:MyAttributeSet.cpp: error C2027: 使用了未定义类型"FGameplayEffectModCallbackData"

原因

该结构体在 AttributeSet.h 里只是前向声明,完整定义在 GameplayEffectExtension.h。这才是真编译错误——与 P1 的假错误对比学习:真错误有 error 编号、文件和行号,出现在 UBT/生成输出里。

解法

cpp 里补 #include "GameplayEffectExtension.h"。通用心法:某个类型"未定义"时,去引擎源码搜它的完整定义在哪个头文件(Grep 搜 struct F名字)。

P12 · git push 到 GitHub 连接被重置 已解决

症状:fatal: unable to access 'https://github.com/...': Recv failure: Connection was reset

原因

本机代理软件(Clash 等)只对走系统代理的程序生效,git 默认直连。

解法

git config --global http.proxy http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897

代理软件关闭后若推送失败,取消:git config --global --unset http.proxy(https 同理)。端口以你的代理软件实际监听为准(netstat -an | findstr LISTENING 查)。

P13 · 引擎/编辑器首次启动特别慢 正常现象

症状:首次打开工程卡很久,日志狂刷 LogShaderCompilers;19GB 素材工程首次加载更慢

定性

首次启动要编译全部着色器变体 + 建立 DDC 缓存,正常现象,等。之后的启动会快很多。日志里 Failed to load 'aqProf.dll' / 'VtuneApi.dll' 是无害的可选性能分析工具缺失,忽略。

P14 · 游戏模块不加载(GE 里找不到自定义属性 / 蓝图搜不到 C++ 类) 已解决

症状:GE 修饰符的 Attribute 下拉只有引擎自带属性;蓝图"选择父类"里搜不到自己写的 C++ 类。编辑器能正常打开,日志无任何报错

原因

.uproject 里的 "Modules" 数组被清空成了 []。本工程是在编辑器里开关插件(VisualStudioTools)时,编辑器重写 .uproject 顺带把模块注册清空的。Modules 数组是引擎加载游戏模块的花名册——空了,编译好的 dll 就永远不被加载,而且全程静默,没有任何报错,排查方向极具迷惑性。

解法

  1. 打开 .uproject,确认 Modules 数组包含游戏模块: 
    "Modules": [
  {
    "Name": "ProjectUnreal",
    "Type": "Runtime",
    "LoadingPhase": "Default"
  }
]
  2. 重启编辑器

验证方法

  1. 日志 Saved/Logs/ProjectUnreal.log 里搜 InternalLoadLibrary: 'ProjectUnreal'——有这行才是真的加载了
  2. 或 PowerShell:(Get-Process UnrealEditor).Modules | Where-Object {$_.ModuleName -like "*ProjectUnreal*"}

教训

  • "编辑器能打开" ≠ "模块已加载"。涉及 C++ 类的功能(自定义属性、蓝图父类)突然消失时,第一反应查 .uproject 的 Modules 数组
  • 手动编辑过 .uproject 后,留意编辑器再次重写它的时机(开关插件、改项目设置),重要字段要定期检查 git diff
  • 此坑 2026-10-07 实录:GE 属性失踪 → 模块未加载 → Modules 被清空,三级倒查才定位

P15 · World Partition 地图无法用脚本/无头模式搬家 已定性

症状:用 Python(rename_asset / AssetRenameData)或裸文件移动 World Partition 地图,改名返回 False 或搬完外部 Actor 全丢

原因

WP 地图的 Actor 分散在 __ExternalActors__/<地图名>/、__ExternalObjects__/ 下一一对应的外部包里,且这些包内部按路径引用地图。挪动地图需要联动迁移这些包并修复双向引用——这套管线只有编辑器 GUI(内容浏览器拖拽)完整驱动;无头 Python 的 rename 系列 API 对 World 资产静默失败(返回 False,无报错)。裸移文件则会留下断链。

解法

在编辑器内容浏览器里拖拽移动(右键 → 移动到),编辑器会自动迁移外部包并修引用。涉及"启动默认图"的,搬完同步改 Config/DefaultEngine.ini 的 GameDefaultMap / EditorStartupMap。

教训

  • Python 自动化适用于"普通资产"(输入资产、混合空间等),地图/关卡类资产的操作留给 GUI
  • 脚本连续两次同类失败就该停手换 GUI,别在无头模式里硬磕(本次连试 4 次,均属无谓消耗)
  • 试错前先想"这个操作在 GUI 里要几秒"——15 秒能点完的,不值得写脚本

P16 · 按 W 角色向右走 / IMC 修改器脚本设置不生效 已解决

症状:按 W 角色右转;Python 脚本里 map_key 后 set_editor_property("modifiers") 日志成功,但资产里没有修改器(二进制里搜不到 InputModifierSwizzleAxis 字符串)

原因

两个叠加:① Enhanced Input 的开关量输入默认落在 X 轴,W/S 没有 Swizzle 时按下等于"向右";② map_key 返回的 FEnhancedActionKeyMapping 在 Python/蓝图里都是副本,对副本写 modifiers 不会回传到 IMC 的真实数组——且全程无报错,属于静默失败。引擎没有提供任何"原地编辑映射修改器"的 API。

解法

IMC 的修改器只能在编辑器里手动加(打开 IMC → 每行映射 → 修改器下拉 → +)。WASD 标准配法与原理见术语对照表的"Enhanced Input:WASD 修改器原理"一节。

教训

  • "set_editor_property 没报错" ≠ 写进去了——对返回值(而非对象本体)的写操作要验证落盘(二进制搜字符串 / 编辑器里看一眼)
  • 中文界面里 Swizzle 译作"拌和输入轴值"(误译,实为轴值交换),Negate 译作"取反/否定"

P17 · 弹簧臂"相对旋转"设了不生效 已定性

症状:想给相机加默认俯角,把弹簧臂(CameraBoom)的相对旋转 Pitch 设为 -15,PIE 后毫无变化

原因

弹簧臂勾选 bUsePawnControlRotation(使用 Pawn 控制旋转)后,目标旋转会被 Pawn 的视角旋转(PawnViewRotation)整体替换,组件自身的相对旋转被完全忽略。源码实锤:SpringArmComponent.cpp GetTargetRotation()(5.8 第 56~66 行)。继承开关(bInheritPitch/Yaw/Roll)的用途是"某个轴不继承时,退回用相对旋转",不是叠加。

解法(按需求三选一)

需求做法
默认俯角 + 鼠标自由环绕(魂系)改控制器初始俯仰:BeginPlay 里 SetControlRotation(Pitch=-15)。本工程做法:C++ 读 UPROPERTY DefaultCameraPitch(-15),BP 细节面板可调

P26 · 持续移动时无法挥刀:收刀逻辑每帧轮询,竞态掐死激活 已解决

症状:站着不动三连击一切正常;只要按住方向键持续移动,按攻击键完全挥不出刀(GA 激活瞬间即被收刀)。越简单的功能越要警惕"站着行、走着不行"这类帧时序症状。

根因(竞态)

旧实现把收刀政策写在 Move() 输入回调里:每帧检查"攻击中 && State.MoveLocked 未打 → CancelAbilities"。但 GA 激活(State.Attacking 打上)到 ANS_MoveLock 把 State.MoveLocked 打上之间有几帧空窗。按住方向键时 Move() 每帧都跑,这几帧里检查全通过 → 攻击刚激活就被自己收刀,表现为"移动完全覆盖技能输入"。站着不动时没有 Move() 事件,所以永远查不出来。

架构教训(本项目铁律)

C++ 只当标签语义的执行器,政策(什么时候锁/什么时候收刀/什么时候衔接)全部交给配置侧的时间轴:

闸门配置侧(策划可拖帧)代码侧(只执行)
锁移动ANS_MoveLock 的区间MoveLocked>0 → 吞输入
可收刀ANS_MoveLock 的结束帧锁段"开始过"&&攻击中 → 按移动即收刀
可衔接GE_ComboWindow 的授予帧+时长GA 激活所需标签匹配

解法

收刀不再每帧轮询,改由标签生灭事件驱动:RegisterGameplayTagEvent 监听 State.MoveLocked(出现=本段攻击已进锁段,置位 bAttackLockApplied)和 State.Attacking(归零=复位)。"本段攻击已经历过锁段"这个标志天然把"GA 刚激活、ANS 尚未打上"的空窗排除在收刀条件之外——因为锁段开始之前标志不可能为真。收刀点仍然是策划在蒙太奇时间轴上拖出来的 ANS 结束帧。

教训

  • 输入回调里做"每帧政策判断"必然引入竞态;政策判断要挂在状态迁移点(标签生灭)上,而不是挂在连续事件(每帧输入)上
  • "站着行、走着不行"= 有轮询在偷跑,第一反应找每帧回调里的政策代码
  • 连"是否经历过某状态"都要由配置的帧位推出,代码里不许出现与时间轴等价的硬编码判断

症状:GE_Cost 挂在三个 GA 的 Cost 上、修改器 -20 targeting Stamina,磁盘真值逐项验证无误;但挥刀体力纹丝不动,体力条和日志均无变化。中途误报:出生时 GE_InitAttributes 打的一条 [体力] 变动=+0.0 日志在时间轴上与攻击相近,被误判为"Cost 执行了但幅度是 0",排查方向被带偏两轮。

根因

GAS 的 Cost 不是激活时自动扣的。扣款(以及扣款前的"付不付得起"检查)由 CommitAbility 节点统一执行;蓝图 GA 的激活图如果直接从 ActivateAbility 跳去 PlayMontageAndWait,Cost 和 Cooldown 永远不走。日志指认法:给 AttributeSet 的结算日志加上 GE=%s(EffectSpec.Def 名)字段,挥刀后若看不到 GE_Cost 的执行行,即坐实"Cost 从未被调用"。

解法

三个 GA 的 ActivateAbility 入口插入 Commit Ability 节点:成功支 → 原流程;失败支(体力不足)→ EndAbility 退场。附带收益:空体挥不出刀从"想要的规则"变成引擎白送(Cost 检查自动拒绝激活)。

教训

  • GAS 三件套分工:Activation 只负责"能不能激活"(标签),Commit 才负责"付不付得起+扣款";激活成功 ≠ 资源已扣
  • "配置全对但没生效"时,下一步不是反复验配置,是验调用方到底调没调——在结算回调里打印 GE 名字,一行日志定位整条链路断在哪一环
  • 联调日志带上数据源头标识(GE 名/事件名),别只打数值——没有源头的数值日志会把排查带进沟里(本例:把出生时的初始化 GE 当成了攻击时的 Cost)

P28 · 攻击转向不生效: Set Actor Rotation 的 Target 引脚接错 已解决

症状:攻击转向通知能算出正确的输入方向和目标 Yaw,节点也执行了,但角色没有按期望转向。

根因

Set Actor Rotation 的 Target 没有接到 Cast To BP_Player 的 As BP_Player,所以旋转被施加到了错误对象。目标旋转本身正确,不能证明被旋转的是玩家角色。

解法

通知里所有针对玩家的角色读取和写入都使用同一个 As BP_Player 引用,尤其检查 Set Actor Rotation.Target。用户确认改正后转向生效。

教训

  • Blueprint 的节点执行成功、输入值正确,不代表节点作用对象正确;调试时同时核对 Target 引脚
  • 角色 Actor 的 Yaw 与 Skeletal Mesh 的相对 Yaw 可能不同,先确认真正被修改的对象再解释角度差

P29 · 平滑转向仍然瞬间切换:旧的直接旋转链绕过插值节点 已解决

症状:加入 RInterp To Constant 并设置角速度后,攻击依然瞬间跳到目标方向。

根因

Set Actor Rotation.New Rotation 仍接着旧的“方向向量 → Rotation From X Vector”直连输出;新插值节点虽然存在,但它的 Return Value 没有进入实际设置旋转的引脚。

解法

将 Get Actor Rotation 接到插值的 Current,目标方向生成的 Rotation 接到 Target,通知事件的 Frame Delta Time 接到 Delta Time;最后把 RInterp To Constant.Return Value 接到 Set Actor Rotation.New Rotation。旧的直接输出链断开。攻击通知状态每帧读取输入,窗口结束即停止更新。用户确认新方案有效。

教训

  • 平滑/限速节点只有进入最终执行链才生效;检查“最终写入节点的输入来源”,不要只看插值节点是否已放进图表
  • 改接线后检查旧路径是否仍然直连,避免两条逻辑并存时旧路径继续覆盖新结果

P30 · 体力条已满但攻击看似不扣体力:只夹了当前值,基础值仍能超上限 代码已编译,待 PIE 验收

症状:周期体力回复一段时间后,HUD 显示满体力,但攻击偶尔看起来没有扣体力。

根因

MyAttributeSet::PreAttributeChange 只限制当前值,而周期 Gameplay Effect 会执行并修改基础值。基础 Stamina 若累积到 MaxStamina 以上,当前值仍可显示为满;攻击 Cost 先消耗隐藏的超额基础值,当前值和 HUD 因此暂时不变。UE 5.8 的 UAttributeSet 将基础值修改钩子单独提供为 PreAttributeBaseChange,并说明它用于基础值夹限;周期/瞬时执行后的最终值可在 PostGameplayEffectExecute 检查。

解法

在 PreAttributeBaseChange 对 Health/Stamina 限制到各自的 0~Max 范围;在 PostGameplayEffectExecute 对 Stamina 执行后再夹到 0~Max,作为执行效果后的兜底。完成编译后,PIE 验证满值后等待一段时间再攻击,体力应立即下降且永不超过上限。

教训

  • GAS 的属性有 Base Value 与 Current Value;只看 HUD 或只夹 Current Value,无法证明基础值也受限
  • “满值时扣费像失效”要检查原始 Attribute 数值和 Base/Current,不能只看进度条
  • 给上限规则同时考虑当前值变化与基础值变化,并在执行式 GE 后验证最终值

P31 · 停止移动后攻击转回默认朝向:零输入仍进入目标旋转计算 已解决

症状:持续移动时攻击按当前输入正确转向;停下后再攻击则稳定转回角色出生时的默认朝向。

定位

在 ANS_AttackTurnWindow 的 Received Notify Begin 打印 BP_Player.Current Move Input:停止后攻击为 (0,0),移动中攻击为 (1,0)/(-1,0) 等有效输入。由此排除输入没有清零,问题位于零向量继续进入旋转计算。

解法

计算 Vector2D Length(Current Move Input),与 0.1 比较。若长度 <=0.1,Branch True 直接结束本次更新,不执行 Set Actor Rotation;仅 False(有有效输入)进入方向转换和插值。用户确认修复后,停止移动再攻击会保留当前朝向。

教训

  • Vector2D 零输入没有有效方向,不能把零向量交给 Make Rot from X 当作目标朝向
  • 先在通知开始时打印输入,能快速区分“输入缓存错误”与“旋转链误处理零输入”
  • 无有效输入时应跳过朝向写入,而不是猜测或生成默认朝向

P32 · 翻滚被攻击打断后永久无法再次激活：混出后的打断未触发技能收尾 用户确认已解决

症状：翻滚与攻击衔接多次后，角色已经站立，再按翻滚没有反应；GA_Roll 的 ActivateAbility 入口打印也不出现。复现依赖打断时机，不一定每次出现。

证据与机制

运行时调试截图右上显示 BlockedAbilityTags: Ability.Roll (1)，角色 Owned Tags 为空，说明仍保留一份阻止翻滚的计数；这不同于窗口 GE 授予的状态标签残留。GA_Roll 存活时阻止 Ability.Roll，自身未退出就会阻止后续激活。

检查 UE 5.8 源码 AbilityTask_PlayMontageAndWait.cpp：蒙太奇正常开始混出与最终结束是两个时刻。混出后再遭打断时，OnMontageEnded 的 interrupted 分支要求 bAllowInterruptAfterBlendOut 才广播 OnInterrupted；任务结束本身不等于所属 GA 结束。只接 OnCompleted / OnInterrupted / OnCancelled，仍可能漏掉未开启此选项时的这条路径。

修复与验收

  1. 在 GA_Roll 的 PlayMontageAndWait 节点勾选 Allow Interrupt After Blend Out（允许混出后响应打断）。
  2. On Completed、On Interrupted、On Cancelled 分别连接 EndAbility，保留 Stop When Ability Ends。
  3. 测试“翻滚 → 起身混出时攻击 → 攻击结束 → 再翻滚”，确认可再次发动，旧技能退出后 Ability.Roll 阻止计数释放。2026-10-19 用户确认问题解决。

以后如何定位

  • 入口打印放在 ActivateAbility 后、CommitAbility 前；分支成功后的打印不能证明入口是否执行。
  • 故障出现后保留 PIE，控制台执行 showdebug abilitysystem，再执行 AbilitySystem.Debug.SetCategory Ability 查看玩家技能是否仍为 Active；BlockedAbilityTags 计数是线索，技能页能进一步确认活跃实例。
  • 此开关只补齐打断后的退出通知，不决定何时允许取消。允许攻击接管翻滚的时机，仍由蒙太奇通知窗口决定。
  • 不要删除阻止自身的 Ability.Roll 配置来掩盖未结束的技能，也不要无条件在 On Blend Out 结束技能来提前释放仍应生效的动作规则。

P33 · 输入有响应但 GA_Roll 不进入：AbilityRoll 变量默认值为空 用户确认已解决

翻滚技能已授予，左 Shift 已映射，但 ActivateAbility 的入口打印不出现。用户定位为 TryActivateAbilitiesByTag 的 AbilityRoll 标签容器变量默认值为空，填写 Ability.Roll 后成功。创建标签变量不代表已经赋值；需要检查实际传入的容器，而非只看标签注册表。

检查顺序：输入 Started 打印 → 激活节点 Target 为自身 ASC → 标签容器包含 Ability.Roll → StartupAbilities 已授予技能 → 激活返回值。某次打断后才不能重复发动，另查 P32。

P34 · 以为窗口 GE 没挂上，实际攻击输入查了反方向的窗口 查询已修正，用户确认第一版可用

只读检查发现 GE_RollCancelWindow 为 Infinite，授予 State.RollCancelWindow；通知 Begin 与 End 引用正确。明确错误在攻击输入：State.Rolling 为真后查询了 State.RollCancelWindow，应该查询 State.AttackCancelWindow。

标签放置位置用途

State.AttackCancelWindow翻滚蒙太奇允许攻击取消翻滚

P35 · 跳跃技能选成蒙太奇跳转，或提交结果没有进入分支 已纠正

GA_Jump 中不能使用 Montage Jump to Section；它仅跳转蒙太奇章节，不会让角色起跳。从 Cast To BP_Player 的 As BP_Player 引脚拖线搜索 Jump，选择 Target is Character 的版本。

CommitAbility.Return Value 必须连到后续 Branch.Condition。只接白色执行线而条件保持勾选，会固定走 True，忽略提交结果。Can Jump 先判断，成本提交成功才 Jump；失败与 Cast Failed 路径结束技能。

P36 · 跳跃期间仍回复体力：State.Jump 随技能立即结束而消失 用户确认已解决

症状：GA_Jump 有 State.Jump，回复 GE 的持续标签排除列表也有它，但跳到空中仍然回复。

2026-10-19 只读核对两侧标签一致。根因是 Jump → EndAbility：Jump 仅请求起跳，不等待落地，GA 立即结束，ActivationOwnedTags 立即移除。标签寿命没有覆盖期望的腾空过程，回复 GE 配置本身没有错。

修复：Jump → WaitMovementModeChange（New Mode=Walking），On Change → EndAbility。前面的 Can Jump=false、CommitAbility=false、Cast Failed 仍结束技能；不要用等待任务的普通执行输出直接结束。用户确认修复成功。

松开按键继续 Stop Jumping，不因此提前 EndAbility；正常落地时再释放跳跃状态。当前实现不包含未来多段跳等扩展规则。

教训：动作启动节点执行完不等于动作过程结束。需要状态覆盖整个动作时，技能或效果的生命周期必须匹配实际结束事件；不要靠固定 Delay 猜落地时间。
