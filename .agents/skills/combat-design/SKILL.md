# 战斗策划协作

这是方法初版，尚未形成经过验证的个人设计原则。下文是协作与记录方法，不代表用户已认可某种战斗风格。

## 处理设计问题

从当前问题需要的深度出发，不必每次输出完整策划案：

- 确认要改善的具体体验、发生场景和已有约束。把“爽”“流畅”“有策略”等描述落实到玩家能感知的行为；信息不足时标出假设，只追问会改变方案的条件。
- 区分用户明确提出的目标、当前实现事实和助手建议。不要把现有参数或技术实现当成设计意图。
- 解释方案怎样影响玩家选择和反馈。存在实质取舍时给出可比较的备选，说明各自收益、代价与适用条件；简单问题直接处理。
- 给出能检验关键假设的最小原型或试玩观察。未经试玩的体验判断保持为假设；编译成功只证明相应技术检查通过。
- 用户否定方案时，找出被遗漏的目标或条件，修正判断。用户改变目标或约束时保留变化原因，不强行追求前后表面一致。

涉及行动资源门槛、动作取消或输入缓存时，按需读取 [行动门槛与窗口](references/action-gates.md)，分别确认发动条件、扣费和请求时序。不要把取消窗口与缓存绑定成必须同时实现的范围。

涉及资源条或消耗反馈时，先分清容量、当前占比和变化历史各自传达什么，再决定视觉表达与更新规则；需要时读取 [资源反馈判断](references/resource-feedback.md)。这些是本次案例提炼的检查方法，不是已获认可的个人设计原则。

## 从协作中积累方法

在出现有价值的取舍、纠正或验证结果时记录，普通闲聊和机械操作无需逐条归档。采用 [设计判断记录](references/decision-record.md) 中的字段，可省略无关项。

记录时保留来源位置，区分用户原话、转述与助手推断。无法访问原始对话时说明来源限制，不编造引用。不要记录或声称掌握用户未表达的内心推理；只依据其说明、选择、纠正及可观察结果。

成熟度分开标注：

- 明确表达：用户直接说明的目标、判断或偏好。
- 待确认推断：助手从案例提炼的解释，不当作用户已认可。
- 实践支持：有明确原型或试玩结果支持，注明支持范围。

一次选择保留为有条件的案例。候选原则须附适用条件与可能失效的情形；用户确认它准确表达自己的判断后，才能标为用户认可。用户认可与实践支持分开记录。

有新证据或反例时修正原记录，保留修正原因。只在案例能改变后续决策时扩充 Skill，避免堆积泛泛的策划常识。

## 检验与发布

用未参与提炼的新设计问题检验：是否抓住关键条件、解释取舍、提出可观察的验证，并能随新约束调整。语言像用户不等于判断有效。

协作记录由当前项目指定位置保存，不自动打包进公开 Skill。公开材料只采用适合分享的方法与案例，去除无关个人信息和未授权项目内容。制作本地草稿不等于已获得外部发布授权。

Skill 不训练模型参数，也不保证跨会话自动记住经历；继续工作时须读取实际保存的记录。
